# 50 次真实模型运行验收（2026-08-02）

## 范围与边界

本次验收在本机已保存的五席配置上执行 10 个标准 Council Run。每个 Run 使用四个讨论席和一个总结席，调用的 Provider / model 均为 `CC Switch / gpt-5.6-sol`。题目来自仓库的固定、非实时 `council_benchmark_v1` 资料案例，覆盖决策、事实核查、风险审计和规划。

- 逻辑模型调用预算：50
- 实际完成：10/10 Run，50/50 逻辑模型调用
- Run 状态：全部 `completed`
- 降级 Run：0
- 已记录 Provider Token：269,364 输入、19,937 输出，合计 289,301
- 端到端时长：974.1 秒；单个 Run 中位数 96.4 秒，最大 177.2 秒

原始、本机私有的运行快照在 `evals/results/live-acceptance-50.json`。它不纳入 Git，因为其中包含完整题目与模型输出。

## 调用计数与成本披露

50 次的依据是每个已保存 Run 的 `usage.model_calls`，不是浏览器显示或手工估算。每个 Run 均恰好记录 5 次成功逻辑调用。

本次不能将 CC Switch 的共享 `proxy_request_logs` 窗口直接当作本次成本：同一时间段存在其他本地 Codex 会话，日志共出现 116 条成功请求，无法可靠归属给这 10 个 Run。因此本报告不声称精确上游请求数或费用，也不把共享日志中的金额归到本次验收。

后续版本已增加 Run 级 `provider_attempts` 审计：保存 HTTP endpoint、状态码、耗时、重试次数和上游请求 ID，但不保存 Prompt、密钥或模型正文。运行页、Markdown 和 HTML 导出均显示实际 API 请求成功数。

## 发现与改进

1. API 成功率：10 个 Run 均完成，但旧版无法把单个 Run 与 CC Switch 共享账单日志准确关联。已补 Run 级请求审计和移动端可见的 `API 成功/总数` 状态。
2. 新人易用性：移动端原先隐藏了全部运行元信息，用户看不到模型是否真正连接成功。已把 API 请求状态从隐藏区移至始终可见的调用状态行；旧历史记录明确显示“旧记录未采集”。
3. 成熟度：真实模型链路成功不等于结论已验证。系统仍不应把多席共识标为事实核验；高风险场景仍要求外部证据、专业复核和审批流程。
4. 准确性：本批固定资料题表现良好，但仍存在单模型同源相关性、长答案偏多、无独立盲评、无实时检索和无可归因成本账本等限制。
